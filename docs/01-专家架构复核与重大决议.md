# ADS-REVIEW-003｜跨开源生态的专家级架构复核

> 评审日期：2026-10-31；评审对象：ADS-ARCH-002（设计稿 2.0）、ADS-PLAN-002、ADS-OSS-002。
> 研究范围：公开上游项目/文档及本地既有设计，不等同于工具已安装、实测通过或完成许可证法律审查。
> 决议：**有条件通过产品目标；不批准直接按旧版 39 项任务全面开发。先修订 M0 验证内核与工具选型，再实施。**

## 1. 顶级评审会首先否决什么

ADS-ARCH-002 的三个产品目标应保留：①需求理解完整；②AI 可靠开发；③交付结果可信。真正需要纠正的是**自研边界与验证有效性**。当前设计把 `ads/benchmark`、`ads/engineering/checkpoint`、`ads/assurance`、`ads/discovery` 都设为自研核心，却没有先证明同类开源组件无法满足要求。39 项任务如果并行执行，可能用一个新工程再造旧脚手架的复杂性。

**P0：评测器没有资格直接给候选框架评分。** v2 已提出基准、隐藏集和注入反例，但没有写出评测任务自身的两面校准协议：正确参考实现必须通过、未修复/空补丁必须失败、坏补丁必须按预期失败；最终候选补丁必须脱离 Agent 工作区，在干净只读基准镜像中复跑。SWE-bench Pro V2 已明确使用这种方法，且纠正了部分“描述与隐藏测试冲突”的任务。若不执行该协议，所谓“新框架发现了更多缺陷”依然可能是假阳性。

**P0：Playwright 测试 Agent 不应由 ADS 重新造。** Playwright 已官方提供 planner/generator/healer 及 OpenCode 集成。ADS 应用它做候选生成、执行与定位，但验收 Oracle 必须是只读的外部契约；healer 不能偷偷改预期或通过 Mock 绕过真实接口。ADS 自研的是来源覆盖差集和结果认可，不是浏览器测试生成器。

**P0：先比较完整方案，而不是只比较片段。** Open SWE 包含 GitHub/PR/CI 反馈与持久执行；GSD 包含新上下文与波次执行；HelixHarness 包含框架评测；Spec Kit 已提供实现后的 converge。当前设计在这些能力上有重造风险。先记录可复用的上游接口、许可证、版本、实测收益与退出机制，再决定哪些逻辑需要保留在 ADS。

## 2. 审核问题与判定

| ID | 严重级别 | 专家会问的问题 | 现有设计不足 | 必须改成的验收标准 |
|---|---|---|---|---|
| R01 | P0 | 如何证明评测案例本身不是无效测试？ | 只有 Golden Path/注入要求，缺参考/空补丁双向校准 | 每个 Case 通过参考实现、拒绝空补丁；至少一次误变异反例；失败 Case 不进入评分 |
| R02 | P0 | Agent 能否通过改测试、依赖缓存或隐藏评分器得分？ | 隔离原则抽象，缺执行信任细节 | Agent 仅能提交补丁；重建全新环境，固定锁文件/镜像/网络边界；评分器和隐藏集在外部 |
| R03 | P0 | 为什么自己写 Harness 评测执行器？ | `ads/benchmark` 预先成为新引擎 | 先用 Harbor 承载至少一组任务；仅不满足具体要求才开发最小插件 |
| R04 | P0 | 为什么自造 UI 测试智能体？ | 只选 Playwright runner，忽略自带 Test Agents | 使用官方 planner/generator/healer+OpenCode PoC；生成脚本不等于验收权威 |
| R05 | P0 | 谁发现完全未进入任何 SPEC 的页面/字段？ | 双路径发现设计正确但缺源盘点误差量化 | 分开衡量来源枚举、解析完整性、义务提取召回；抽样复核遗漏而非全靠同一 AI |
| R06 | P0 | 如果原始资料互相矛盾呢？ | `OBSERVATION/CANDIDATE/CONFIRMED` 合理，但权威裁决仍粗 | 引入来源优先级、冲突实例、裁决人、有效适用范围；不得选取最方便测试的版本 |
| R07 | P0 | QA 的独立性来自哪里？ | 独立 Agent 容易仍共享同一错误材料 | 冻结 QA 自己的来源/案例/构建绑定，权限隔离；QA 对开发实现和评分器的写权限为零 |
| R08 | P0 | 实现失败时，Agent 能否修改测试后自称修复？ | 强调禁止但缺机制 | 划分只读外部验收与可改开发测试；对前者提交变化需独立授权；扫描差异和 CI 重跑 |
| R09 | P1 | 持久化 checkpoint 与可靠执行是什么关系？ | JSON checkpoint 不等于事务性/恰好一次执行 | 将每类副作用显式标记为 `read-only/idempotent/reconcilable/manual-only`；重启前核实已执行事实而非只看日志 |
| R10 | P1 | OpenCode 已经有什么原生能力？ | 初步有 SDK/Agent/Skills，但缺逐 API PoC | 当前固定版本真实实测：子代理事件、权限拒绝、工作区、退出结果、中断恢复、进程死亡 |
| R11 | P1 | 标准能力如何减少维护？ | 自研 JSON 执行报告多层 | 直接消费 JUnit XML、Playwright JSON/Trace、OpenAPI、Git commit、CI attestation；仅做最薄证据投影 |
| R12 | P1 | 发布前 E2E PASS 是最终产品正确吗？ | 已提部署烟测，欠明确服务级监控 | 明确部署版本身份、真实 API/DB 依赖、SLO、故障回滚；非功能性可靠性单独报告 |
| R13 | P1 | 对外提供的系统会不会继承有害许可负担？ | 只说许可证审查 | 每项标记 `idea/protocol/API/dependency/copied code`；许可证和 NOTICE、数据来源许可纳入入库审查 |
| R14 | P1 | 如何防止“全部 UNKNOWN 就阻断一切”的假质量？ | UNKNOWN 不通过，但未定适用性裁剪 | 按获批准风险策略、实物特征和受影响范围判适用性；未知应解释影响、由有权者裁决 |
| R15 | P1 | 把 BMAD/GSD 也安装进来会怎样？ | 没明确多框架竞态处理 | 一个主开发入口、一套权威规格、一套有效执行协议；仅借鉴方法与可独立调用能力 |
| R16 | P1 | 测试数量增加是否说明真的更好？ | 已有三轴 KPI，但可能被固定案例过拟合 | 开发集、隐藏保留集、后续新鲜真实案例三层；保留所有失败样本、置信区间和成本 |
| R17 | P1 | UI 自动修复会不会“修坏测试”？ | 自动修复边界偏文字 | 保留脚本 diff、根因、旧新运行 Trace，验收断言变化需审查；关键旅程禁止自动降断言 |
| R18 | P2 | 何时需要云端编排与平台？ | 默认为本地 CLI 正确，但无量化升级条件 | 仅在真实多人并发、跨主机续接、中央审计或资源调度瓶颈出现后，评估服务化 |

## 3. 从不同成熟产品借鉴的真正独到之处

1. **SWE-bench Pro V2**：不是追求更多题，而是修复题目歧义、双向校准、纯净镜像再评分、杜绝 Agent 找到公开修复补丁。我们的 M0 应先评测评分器，不先比较 AI 模型。来源：https://labs.scale.com/leaderboard/swe_bench_pro_public_v2
2. **Harbor / Terminal-Bench**：可复用的任务、隔离环境、Agent 适配和结果采集。评测基础设施不是 ADS 独门能力。来源：https://github.com/harbor-framework/harbor
3. **Playwright Test Agents**：planner → generator → healer，已支持 OpenCode。即使生成测试充分，也仍需保持受控验收预期与真实后端。来源：https://playwright.dev/docs/test-agents
4. **Open SWE / LangGraph**：代码调研、实现、PR、CI 反馈形成真实工程闭环；它的持久执行比单个 checkpoint JSON 更具操作语义。但其部署可能依赖托管组件，应进行成本和权限 PoC。来源：https://github.com/langchain-ai/open-swe
5. **GSD**：薄协调器、新鲜上下文、依赖波次、项目状态；其默认“未配置即启用”并不适合安全硬门禁，照搬会引入隐式放行风险。来源：https://github.com/gsd-build/get-shit-done/blob/main/docs/ARCHITECTURE.md
6. **Spec Kit**：不仅事前分析一致性，已有 `converge` 事后检测规格与实现差距，值得与 OpenSpec Verify 做基准比较，而不是增加第二套规格。来源：https://github.github.com/spec-kit/
7. **BMAD**：Analyst、PM、PO、UX、开发和专用测试角色，不同视角改善发现质量；但角色更多并不等于有独立证据。来源：https://github.com/bmad-code-org/BMAD-METHOD
8. **Docling**：PDF/图片/表格/录屏可成为结构化源，解析覆盖率仍需用定位与人工抽样校准。来源：https://github.com/docling-project/docling
9. **Opik / Phoenix**：轨迹、数据集、模型实验、人工反馈与分析已有成熟能力。先采用 OpenTelemetry 字段，再对比外部平台，避免自研监控仪表盘。Phoenix 采用 ELv2，许可需要特别核实。来源：https://github.com/comet-ml/opik 、https://github.com/Arize-ai/phoenix
10. **GitHub Artifact Attestations**：已有 OIDC 身份绑定构建出处，不必先自研签名协议；但出处可信≠业务结果正确。来源：https://docs.github.com/en/actions/concepts/security/artifact-attestations

## 4. 重新划定三个主系统的自研范围

### 需求智能：自研“跨来源交付义务核对”而非文档解析器

Docling、原生 Excel 解析、Figma 结构化源负责获取内容；人工或业务端决定已确认的约束。ADS 只维护可复现来源清单、候选与确认边界、源→义务→验收的差集、未知范围和反例提问。**完整性不可能绝对证明，必须给出范围及遗漏风险，而不写一个虚假的 100%。**

### AI 可靠开发：优先 OpenCode 原生机制+可测的薄工作流

先在真实 OpenCode 上完成一条任务：发现 → 设计 → 启动项目 → 垂直切片 → 真实测试 → 自动调试 → PR/CI 反馈。对比 GSD/HelixHarness/Open SWE 的具体机制；仅在 OpenCode 对恢复、跨仓或上下文失效能力确有缺口时开发 Adapter。**不要造第二个 Agent Loop。**

### 可信交付：复用真实测试器和评测引擎，自研决策投影

开发侧可以生成和修复测试，但正式验收预期由外部只读来源+独立 QA 控制。真实测试由专业 runner 提供，CI 产生可信身份；ADS 的判定层仅接受完整实体、已执行结果和策略。输出包含业务完整性、开发可靠性、真实可用性、QA 和证据身份，绝不合并成一个模糊 PASS。

## 5. 实施上的明确停止线

- **M0 不通过**：无法证明参考实现通过、空补丁失败、错误实现失败，禁止开发核心 Harness 评分器。
- **Playwright Agent PoC 能用**：删除“自研 UI 测试生成/修复器”的研发项；只保留只读验收约束与 Adapter。
- **Harbor PoC 能用**：删除“自研 Agent 评测执行平台”的研发项；只保留任务和评分器 Adapter。
- **OpenCode 原生机制已覆盖**：删除重复的工作流状态/检查点逻辑。
- **QA 无独立证据**：不因 DEV 全绿而允许 QA PASS。
- **无受保护 CI**：可以报告本地开发验证，但不能宣称发布级可信。
- **现有基线已经能以更低成本完成任务**：候选方案不得只凭更多文档和检查赢得比较。

## 6. 评审结论

**保留 ADS 三目标；调整四项研发优先级：先确认评分可信→再选复用工具→再建完整性层→最后根据数据补可靠执行能力。** 重新设计 QA 的独立输入和只读验收权威；把静态检查、运行结果、风险决定、交付出处分别报告。下一轮不应把 `ADS-ARCH-002` 的 39 个任务当不可修改的承诺。
