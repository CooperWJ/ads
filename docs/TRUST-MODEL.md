# M0a 评测信任模型与严格校准运行要求

## 哪些成果已经真实执行

M0 案例在临时目录中应用单一补丁、启动 Python HTTP 服务、查询 SQLite 和读取 XLSX。Node integration 以独立维护的有限 DOM 运行实际候选 JS 代码，并访问真实 HTTP 服务。评测器有正例、空解、错误变异与等价实现校准。

## 哪些信任边界仍缺失

- `tempfile` 不等于权限隔离。Python 候选服务、Node `vm` 内的脚本都有机会通过执行环境漏洞影响宿主；`vm` 不是安全沙箱。禁止在高权限或携带 secrets 的机器执行不可信补丁。
- `check_evidence()` 的 `current/stale` 是**合成输入**。它验证评分器对明显错误 SHA 的处理，但当前没有独立的外部签名者、可信部署身份或不可篡改结果存储。
- `check_qa()` 的必验集合也是评测方准备的合成状态，不构成真实 QA 已验收。
- 当前仓库内的 GitHub Actions 流程同样可以被有写权限的人改动，它不是独立可信 CI。任何本仓测试结果只能声称“自测”。
- 只有当隐藏预期和评测代码由受保护的独立执行方持有、候选不能访问或修改，并在干净环境中重新构建/执行时，才能提高独立证据等级。

## 独立 Runner 设计（尚未完成/部署）

1. 在受保护的独立仓库存放评测器、原始 Oracle 与参考解；对受测 Agent 仅提供任务输入与初始工程。
2. 用独立只读 checkout 接收候选 Git patch，拒绝越权路径修改；不暴露 CI 身份凭据给候选进程。
3. 为候选提供无 secrets 的容器或其他 OS 隔离，按固定镜像版本重建环境。仅允许必要 HTTP；默认最小网络权限。
4. 独立评分器在受保护环境获取执行结果；对源码提交、构建/镜像摘要、环境身份和执行日志进行绑定。
5. 外部评分后再次校验空解 FAIL、故意坏变异 FAIL、参考解 PASS，避免测试被改坏而悄悄放行。
6. 正式 QA 验收用独立来源、独立人员/账号；不能直接用 Agent 编写的 QA 结果替代。

## GitHub Actions 自测模板

`.github/workflows/m0-selftest.yml` 使用 Node 22 + Python 3.13 + pinned Playwright 安装并运行 `--require-browser`；没有声明具备保护机制。它不包含授权凭据。可信生产设计需要将验证工作流及评分器放在无法被候选修改的权限域，受保护分支策略由仓库管理员实际配置。

## 当前禁止的声明

- 不能说 Node fake-DOM PASS 等于真实浏览器 E2E PASS。
- 不能说 Git patch 白名单等于程序执行沙箱。
- 不能说内部 SHA 比对等于独立软件供应链证明。
- 不能说合成 QA 所有用例通过等于真实项目 QA 验收完成。
